October opened with a week of authentication hardening and a new self-service sign-up flow (verification codes, invitations, a bot check), then built SMART App Launch out from standalone to EHR launch: a `$launch` operation, launch context carried on tokens and refresh tokens, and `patient/` scopes bound to one compartment. Mid-month rebuilt the server's request pipeline around typed lanes, exposed every FHIR operation as an MCP tool with a conformance suite behind it, and landed the FHIR asynchronous request pattern. The last ten days were worked largely from the new agent task board: dozens of FHIRPath functions and operators, a dozen FHIR search result parameters and prefixes, `AccessPolicyV3` and `DeidentificationPolicy` definitions, a TestScript suite for the ONC (g)(10) test kit, and a conformance site that reports every suite. The final week, through November 1, closed out SQL on FHIR against a TestScript suite built from the specification's tests, ran the HL7 FHIRPath test suite inside the crate and fixed what it found, added `_revinclude`, `ImplementationGuide/$install` for FHIR packages, token introspection and a consent screen that grants a subset of scopes, and brought US Core 7.0.0 and CARIN Blue Button suites into CI beside the (g)(10) kit, which now runs on US Core 7.0.0.

## Backend Changes

### SMART App Launch: EHR launch
- `ClientApplication/{id}/$launch` starts an EHR launch of an app for a patient and, optionally, one of the patient's encounters. Haste Health plays the EHR: the operation saves the launch context and returns the app's `launchUri` (a new `ClientApplication` element) with `iss` and `launch` added to its query. The launch value expires after five minutes, only a signed-in user can start one, and the same user must then authorize the app.
- The authorize endpoint accepts `launch` alongside the `launch` scope and resolves it before consent, so nobody is asked to approve an app for a launch that cannot be used, and an `aud` parameter must name the project's FHIR base URL. The token response carries `patient`, `encounter` and `need_patient_banner`, the launch context rides on the refresh token so a refreshed token stays bound to the same patient and encounter, and a user who is a patient may only launch an app for themselves.
- Follow-ups from the (g)(10) work: `smart_style_url` in launch token responses, backed by a `smart-style.json` endpoint; the OpenID configuration served at the id token issuer (`/w/{tenant}/{project}/.well-known/openid-configuration`) with the SMART configuration's `issuer` matching it; an unparseable scope redirected to the registered `redirect_uri` with `error=invalid_scope` and `state` instead of answered with a 501; and `authorize-post`, `permission-v1`, `context-banner`, `context-standalone-patient` and `context-style` advertised as capabilities.
- A public client may omit `client_id` when refreshing, since the refresh token names the client it was issued to. The SMART on FHIR and client registration docs were rewritten around the flow.
- The token endpoint answers as RFC 6749 writes it: a bad, expired or reused code or a PKCE verifier mismatch is `invalid_grant` (400), a wrong or missing client secret or an unknown `client_id` is `invalid_client` (401 with `WWW-Authenticate`) instead of `access_denied` or a 500, and every response from the endpoint carries `Cache-Control: no-store` and `Pragma: no-cache`.
- PRs: [#1057](https://github.com/HasteHealth/HasteHealth/pull/1057), [#1059](https://github.com/HasteHealth/HasteHealth/pull/1059), [#1062](https://github.com/HasteHealth/HasteHealth/pull/1062), [#1065](https://github.com/HasteHealth/HasteHealth/pull/1065), [#1066](https://github.com/HasteHealth/HasteHealth/pull/1066), [#1067](https://github.com/HasteHealth/HasteHealth/pull/1067), [#1070](https://github.com/HasteHealth/HasteHealth/pull/1070), [#1068](https://github.com/HasteHealth/HasteHealth/pull/1068), [#1315](https://github.com/HasteHealth/HasteHealth/pull/1315), [#1316](https://github.com/HasteHealth/HasteHealth/pull/1316), [#1317](https://github.com/HasteHealth/HasteHealth/pull/1317), [#1321](https://github.com/HasteHealth/HasteHealth/pull/1321), [#1322](https://github.com/HasteHealth/HasteHealth/pull/1322), [#1395](https://github.com/HasteHealth/HasteHealth/pull/1395).

### Patient-scoped access
- SMART v1 `patient/` scopes are issued as read and search only, bound to one Patient compartment. The patient comes from the Membership's link or from the EHR launch; a patient-bound scope with no patient in context is dropped rather than issued unbound, and the response's `scope` tells the client what was issued.
- A search on a compartment type runs with a filter over the R4 compartment parameters, a read outside the compartment answers exactly as one that does not exist, and writes, history, system-level search, chained and `_has` parameters are refused because none of them can be bounded. Reference data that no `CompartmentDefinition` can place (shared types) stays readable as a whole.
- R4's Patient `CompartmentDefinition` lists `Device` with no parameter, so a patient scope refused every Device request and `Patient/[id]/Device` found nothing. A patch on the hl7-core package links Device to the compartment through its `patient` search parameter, and everything that reads the definition follows: the patient-scope filter, reads outside the compartment (404), `Patient/[id]/Device` and `$everything`. Two (g)(10) Device checks left the known failures.
- TestScript suites under `backend/testscripts/access-control` cover patient, user and system scopes and the SMART launch. A headless login script and an access-control workflow run them in CI, and the CLI gained `login --no-browser` and `admin user set-password` so a pipeline can sign in without a browser.
- PRs: [#1048](https://github.com/HasteHealth/HasteHealth/pull/1048), [#1049](https://github.com/HasteHealth/HasteHealth/pull/1049), [#1052](https://github.com/HasteHealth/HasteHealth/pull/1052), [#1428](https://github.com/HasteHealth/HasteHealth/pull/1428).

### Consent, scope ceilings and token introspection
- The scope approval page lists each requested scope with a checkbox, all checked, so the user can grant an app a subset of what it asked for; `openid` and the launch context scopes stay checked because the flow needs them. The code and the token are issued for the approved scopes only, approving none counts as a denial, and the headless sign-in script can uncheck scopes, which the (g)(10) limited-access scenario uses to request every US Core type and grant three.
- A client's registered scopes are a ceiling checked by coverage rather than by string: `patient/*.rs` covers `patient/Medication.rs`, and `patient/Medication.rs` covers `patient/Medication.s`, while a write permission never implies a read. Six access-control TestScripts pin the granted and refused cases for patient and system scopes.
- `POST [base]/oidc/auth/introspect` lets a resource server check an access token the server issued, authenticated as a confidential client of the project. A token is active when the project's FHIR API would accept it, and the response carries `scope`, `client_id`, `exp`, `sub`, `aud`, `iss`, `fhirUser` and the launch context (`patient`, `encounter`, `need_patient_banner`, `smart_style_url`); anything else answers `{"active": false}`. Access tokens now carry `client_id` (RFC 9068) and the launch's encounter, and the SMART configuration lists `introspection_endpoint`.
- PRs: [#1414](https://github.com/HasteHealth/HasteHealth/pull/1414), [#1394](https://github.com/HasteHealth/HasteHealth/pull/1394), [#1415](https://github.com/HasteHealth/HasteHealth/pull/1415).

### Asynchronous requests
- Operation invocations accept `Prefer: respond-async`: the server queues a job, answers `202 Accepted` with the job's status URL in `Content-Location`, and runs it in the background with exactly the permissions the request had. Every check the synchronous form makes (authentication, scopes, access policies, rate limits, that the operation exists) happens before the job is accepted.
- `GET` on the status URL answers `202` with `X-Progress` and `Retry-After` while the job runs, then the response the synchronous request would have had, or the operation's own error. `DELETE` cancels. Results stay available for 24 hours by default, a project may have ten queued or running jobs at once, and the CORS layer exposes the headers a browser client needs.
- Jobs live in a new `async_jobs` table and run from the worker, which split into `haste-health worker indexing` and `haste-health worker async-jobs` so the two can scale on their own.
- PRs: [#1115](https://github.com/HasteHealth/HasteHealth/pull/1115), [#1116](https://github.com/HasteHealth/HasteHealth/pull/1116), [#1273](https://github.com/HasteHealth/HasteHealth/pull/1273), [#1274](https://github.com/HasteHealth/HasteHealth/pull/1274), [#1275](https://github.com/HasteHealth/HasteHealth/pull/1275), [#1276](https://github.com/HasteHealth/HasteHealth/pull/1276).

### FHIRPath
- The evaluator closed most of its gap to the specification. New functions: `all`, `allTrue`, `anyTrue`, `allFalse`, `anyFalse`, `subsetOf`, `supersetOf`, `distinct`, `isDistinct`, `select`, `single`, `last`, `tail`, `skip`, `take`, `union`, `combine`, `intersect`, `exclude`, `iif`, `not`, the math functions, `indexOf`, `substring`, `length`, `toChars`, `replace`, `matches`, `replaceMatches`, `startsWith`, `endsWith`, `contains`, `trace`, `is`, every `toX` and `convertsToX` conversion including dates, times and quantities, `now`, `today`, `timeOfDay`, and `$index` inside iteration functions.
- New operators: `in`, `contains`, `implies`, `div`, `mod`, unary `+` and `-`, `&`, `~` and `!~`, and ordered comparisons on strings as well as numbers. Date, DateTime, Time and Quantity literals parse, and `+` and `-` work between a date or time value and a time-valued quantity, with month ends clamped. The parser resolves string escapes (so the regexes in R4 invariants reach `matches` intact) and accepts comments.
- The FHIR-specific functions (`extension`, `hasValue`, `getValue`, `htmlChecks`, `memberOf`, `subsumes`, `subsumedBy`, `conformsTo` and a real `resolve`) arrived behind a `FHIRServices` trait; the server does not wire its terminology service into it yet.
- `and`, `or` and `xor` follow three-valued logic for empty operands. This changes what `Patient-deceased` indexes for patients without `deceased[x]`, so existing Patient data needs a reindex.
- Compiled regular expressions are cached by pattern, like the expression ASTs, and the specification's own examples run as tests in the crate.

### FHIRPath: the HL7 test suite
- The HL7 FHIRPath test suite (1,055 cases) runs as a test of the `fhirpath` crate against a `known_failures.txt` that every fix shrinks and CI regenerates. It went in at 738 passing and ends the month at 859; what remains is filed as issues under the FHIRPath umbrella, with the fixes below coming through the task board.
- Dates, dateTimes and times compare: `=`, `~` and the ordering operators go one precision at a time, give empty when one value stops before the other, and compare offsets in UTC. DateTime literals may stop at the hour or minute (`@2015-02-04T10:00`), held as the engine's own partial DateTime so the FHIR model and search indexing are unchanged, and the other comparisons settle the type by name first so they run as fast as before.
- Quantities: same-unit quantities compare by value and a unary minus negates one; a calendar duration keyword and its UCUM unit are one unit at week and below (`7 days = 1 week`) while year and month compare only with the same unit; `toString()` prints `1 week` and `1 'wk'` rather than `1.0 'week'`; and adding `'mo'`, `'a'` or a non-time unit to a date is an error rather than empty.
- Numbers and collections: `+`, `-` and `*` on two integers give an integer (empty on overflow) and `/` by zero gives empty; `=` and `!=` compare whole collections in order; `positiveInt` and `unsignedInt` take part in comparison and arithmetic; and `repeat()` adds a projected item only when no equal item is already in its output, so a projection that keeps yielding new values is stopped by a 10,000 item budget per evaluation rather than running forever.
- Types, variables and the parser: `is`, `as` and `ofType` resolve `FHIR.` and `System.` qualifiers and the System type names, with System types matching only values the engine made, as the suite requires; `%sct`, `%loinc`, `%ucum`, `%vs-[name]` and `%ext-[name]` are defined by the engine; and the parser accepts backtick identifiers, requires four hex digits after `\u`, allows line breaks in strings and whitespace before a unary minus. `trim()` came from an outside contributor (below), and `replaceMatches('', x)` returns its input unchanged.
- PRs: [#1334](https://github.com/HasteHealth/HasteHealth/pull/1334), [#1331](https://github.com/HasteHealth/HasteHealth/pull/1331), [#1332](https://github.com/HasteHealth/HasteHealth/pull/1332), [#1397](https://github.com/HasteHealth/HasteHealth/pull/1397), [#1386](https://github.com/HasteHealth/HasteHealth/pull/1386), [#1388](https://github.com/HasteHealth/HasteHealth/pull/1388), [#1390](https://github.com/HasteHealth/HasteHealth/pull/1390), [#1387](https://github.com/HasteHealth/HasteHealth/pull/1387), [#1389](https://github.com/HasteHealth/HasteHealth/pull/1389), [#1347](https://github.com/HasteHealth/HasteHealth/pull/1347), [#1400](https://github.com/HasteHealth/HasteHealth/pull/1400), [#1403](https://github.com/HasteHealth/HasteHealth/pull/1403), [#1385](https://github.com/HasteHealth/HasteHealth/pull/1385), [#1391](https://github.com/HasteHealth/HasteHealth/pull/1391), [#1405](https://github.com/HasteHealth/HasteHealth/pull/1405).

### FHIR search: result parameters and prefixes
- `_include=*` and `Type:*` expand to every reference parameter of the matched types; a system-level search resolves `_include` and marks every entry's `search.mode`; `_type` filters a system-level search; `_count=0` returns an accurate total with no entries; `_sort` accepts number, quantity and uri parameters; `_summary=data` drops `text`, and matches trimmed by `_elements` or `_summary` carry the `SUBSETTED` tag; `_format` and `_pretty` are accepted on searches; and `_list` restricts a search to a List's items (PostgreSQL only).
- URI parameters gained `:above` and `:below`. Escaped `\,`, `\|` and `\$` in parameter values are honored by the server and the TypeScript client, and `ne` on a quantity negates the whole match, value and unit, on every backend.
- Modifier and prefix parsing moved into shared enums used by the PostgreSQL, Elasticsearch and in-memory backends, and the in-memory backend now runs the same clause semantics as the other two.
- New TestScripts pin `:missing` across parameter types, `eq` on numbers with the specification's precision examples, and every quantity prefix.
- PRs: [#1074](https://github.com/HasteHealth/HasteHealth/pull/1074), [#1235](https://github.com/HasteHealth/HasteHealth/pull/1235), [#1251](https://github.com/HasteHealth/HasteHealth/pull/1251), [#1252](https://github.com/HasteHealth/HasteHealth/pull/1252), [#1253](https://github.com/HasteHealth/HasteHealth/pull/1253), [#1254](https://github.com/HasteHealth/HasteHealth/pull/1254), [#1259](https://github.com/HasteHealth/HasteHealth/pull/1259), [#1260](https://github.com/HasteHealth/HasteHealth/pull/1260), [#1261](https://github.com/HasteHealth/HasteHealth/pull/1261), [#1262](https://github.com/HasteHealth/HasteHealth/pull/1262), [#1263](https://github.com/HasteHealth/HasteHealth/pull/1263), [#1266](https://github.com/HasteHealth/HasteHealth/pull/1266), [#1267](https://github.com/HasteHealth/HasteHealth/pull/1267), [#1268](https://github.com/HasteHealth/HasteHealth/pull/1268), [#1269](https://github.com/HasteHealth/HasteHealth/pull/1269), [#1271](https://github.com/HasteHealth/HasteHealth/pull/1271), [#1285](https://github.com/HasteHealth/HasteHealth/pull/1285).

### FHIR search: `_revinclude`, project parameters and embedded resources
- `_revinclude` resolves from the page the backend returned, like `_include`: one search per directive per hop with every page id as the value, answered from the reference index and confined to the caller's compartment. `:iterate` follows the referrers of what an earlier hop added in either direction, system-level searches get the same, and the bounds on included resources, results per directive and iteration depth truncate rather than fail. A base TestScript covers ten shapes of the parameter, and 42 (g)(10) checks left the known failures.
- Repeated query parameters survive parsing: `_revinclude=A&_revinclude=B` kept only the last one, since the query string was collected into a map. It is now parsed as ordered pairs (an outside contribution, below), and a `_search` body is combined with the query the same way.
- A project's own `SearchParameter`s are resolved by one resolver shared by the PostgreSQL and Elasticsearch backends and cached per process for fifteen minutes, with two early refreshes: the indexing worker indexes a batch's `SearchParameter`s first and drops the project's copy, and a lookup by name that misses rebuilds it once, so a new parameter is searchable as soon as it is indexed. A TestScript creates a parameter and searches by it.
- Bundle `composition` and `message` select the first entry's resource rather than a Reference, so they never matched: `:missing=true` found every Bundle and an id found none. Reference indexing now indexes an embedded resource as its own type and id on all three backends, and a patch narrows the two expressions to `as Composition` and `as MessageHeader`, as R5 does. Chaining into the embedded resource is not supported.
- `:exact` on a string compares `LOWER(value)` as well as the value itself, so the lowered index finds the rows while the match stays case-sensitive; the bare equality read every row of the parameter.
- PRs: [#1396](https://github.com/HasteHealth/HasteHealth/pull/1396), [#1406](https://github.com/HasteHealth/HasteHealth/pull/1406), [#1326](https://github.com/HasteHealth/HasteHealth/pull/1326), [#1413](https://github.com/HasteHealth/HasteHealth/pull/1413), [#1409](https://github.com/HasteHealth/HasteHealth/pull/1409).

### Search totals
- `_total=estimate` and `_total=accurate` on PostgreSQL count exactly up to a bound (10,000 rows or 100 ms for an estimate, 50,000 rows or 500 ms for accurate) before falling back to the planner's estimate, and the page corrects the result: a short page is exact, a full page is a lower bound, an empty page past the start is an upper bound. A TestScript checks the total on every page shape.
- PRs: [#1108](https://github.com/HasteHealth/HasteHealth/pull/1108), [#1260](https://github.com/HasteHealth/HasteHealth/pull/1260).

### SQL on FHIR
- A TestScript suite under `backend/testscripts/sql-on-fhir`, built from the specification's test cases, runs in its own e2e workflow with the scripts that fail listed by cause in `known-failures.txt`. It went in at 48 of 106 passing; the first run's failures were filed as issues, and the fixes below leave it at 89 of 108.
- `$viewdefinition-run` keeps only resources of the view's `resource` type (a Bundle of another type still stands for its entries); a column typed with a FHIR primitive accepts the FHIRPath System value that maps to it, so an `id` column fed `Resource.id`, a literal or `%rowIndex` no longer fails; and integer, boolean and decimal constants reach FHIRPath as primitives rather than as the choice enum that held them.
- Nested `select` and `unionAll` are evaluated recursively per focus node (own columns, nested rows and union branches in order), and `forEachOrNull` over nothing gives one all-null row covering the nested columns. `repeat` is walked by the runner rather than by FHIRPath's `repeat()`: every path from each node, each item emitted and then walked the same way, once by identity and under the 10,000 item budget, so `repeat: ["$this"]` answers one row instead of hanging.
- A `where` path that evaluates to empty excludes the resource, an undefined constant is an error (400) rather than empty, and an invalid FHIRPath expression anywhere in the view answers 400 instead of 500.
- PRs: [#1333](https://github.com/HasteHealth/HasteHealth/pull/1333), [#1330](https://github.com/HasteHealth/HasteHealth/pull/1330), [#1329](https://github.com/HasteHealth/HasteHealth/pull/1329), [#1349](https://github.com/HasteHealth/HasteHealth/pull/1349), [#1348](https://github.com/HasteHealth/HasteHealth/pull/1348), [#1351](https://github.com/HasteHealth/HasteHealth/pull/1351), [#1345](https://github.com/HasteHealth/HasteHealth/pull/1345), [#1346](https://github.com/HasteHealth/HasteHealth/pull/1346), [#1353](https://github.com/HasteHealth/HasteHealth/pull/1353).

### Operations
- A `GET` on `/$op`, `/[type]/$op` or `/[type]/[id]/$op` runs the operation when its `affectsState` is false, with the query string typed into `Parameters` from the `OperationDefinition`. A state-changing operation answers 405, and the destructive built-ins (`$delete-refresh-token`, `$delete-scope`, `$launch`, `$tenant-customization`) are now marked `affectsState = true`.
- The built-in operations' `OperationDefinition` resources are served beside a project's own through an in-memory search backend: a read of a built-in's id returns it, a type search lists it ahead of the project's, and a project definition that would shadow a built-in is refused.
- Invocation responses come back at the level they were invoked at, so the typed client methods work for instance and type invocations, and `ValueSet/{id}/$expand` and `$validate-code` read the instance they target. `$viewdefinition-run` no longer needs `_since`: it walks the type's history, keeps each resource's current version, leaves deleted ones out, and the Binary it returns carries a `contentType`.
- A resource that fails profile validation answers 422 with the validator's OperationOutcome, and the `structure`, `required`, `value` and `invariant` issue codes map to 400; both were 500s. The CapabilityStatement lists every active constraint StructureDefinition in the project under `rest.resource.supportedProfile` and the project's active SearchParameters under `searchParam`, and its cache expires after thirty seconds so profiles loaded later appear without a restart.
- PRs: [#1319](https://github.com/HasteHealth/HasteHealth/pull/1319), [#1074](https://github.com/HasteHealth/HasteHealth/pull/1074), [#1107](https://github.com/HasteHealth/HasteHealth/pull/1107), [#1314](https://github.com/HasteHealth/HasteHealth/pull/1314), [#1318](https://github.com/HasteHealth/HasteHealth/pull/1318).

### Implementation guides
- `ImplementationGuide/$install` installs a FHIR package into a project from the package registry (`name@version`, `name@6.1.x`, or `name` for the latest) or from an uploaded `.tgz`, with the packages it depends on, breadth first; the FHIR core and large terminology packages are skipped by default. A package's StructureDefinitions, ValueSets, CodeSystems, SearchParameters, ConceptMaps and NamingSystems are written in one transaction under their package ids, tagged with the package and recorded as an `ImplementationGuide` named for it. Reinstalling replaces the installed version and deletes what it no longer has, resources the package did not install are never replaced, `$uninstall` reverses it, and the canonical resolver forgets the project's entries on install so installed profiles apply at once.
- The install is bounded: packages come only from the configured https registry (redirects stay on it, and an empty registry URL allows uploads only), one install may fetch at most 50 packages and unpack 200 MiB, one install runs at a time per server by default, and the Free tier may start one install every two minutes, with one Free tier install a minute across all tenants. Da Vinci PDex 2.2.0, QI-Core 7.0.2 and US Core 9.0.0 fit the defaults.
- A new `fhir-package` crate reads packages under size and file limits and talks to the registry. The CLI gained `package install | uninstall | list`, the admin app a Packages page, the docs an Implementation Guides guide, and the US Core and (g)(10) pipelines install their packages through `haste-health package install <folder> --no-dependencies` instead of a script, which puts the CLI and `$install` under CI.
- PRs: [#1416](https://github.com/HasteHealth/HasteHealth/pull/1416), [#1418](https://github.com/HasteHealth/HasteHealth/pull/1418), [#1420](https://github.com/HasteHealth/HasteHealth/pull/1420).

### Profile validation
- A slice defined by its binding alone (no `fixed[x]` or `pattern[x]`) is matched by a `value` discriminator through the codes its required value set's `compose` allows, read without expanding it, so US Core's category slices validate. A `pattern` discriminator is checked the same way as `value`, which R4 gives the same rule and R5 deprecates as a synonym; US Core 7.0.0 slices category with `pattern` on binding-only slices, which had failed in 89 TestScripts.
- `fixedBoolean`, `fixedInteger`, `fixedDecimal`, `fixedPositiveInt` and `fixedUnsignedInt` refused every resource claiming the profile with "Failed to downcast value to boolean": the reflection layer's `Box<T>` handed back the Box instead of its content on a downcast. A Box is now transparent, and a base TestScript creates profiles with each fixed primitive and checks that differing resources are refused.
- PRs: [#1402](https://github.com/HasteHealth/HasteHealth/pull/1402), [#1412](https://github.com/HasteHealth/HasteHealth/pull/1412), [#1426](https://github.com/HasteHealth/HasteHealth/pull/1426).

### Error origins
- `OperationOutcomeError` records where it came from: the construction site (`track_caller` on the constructors and the derived `From`, so a `?` is the origin), a context trail, the source chain, and a backtrace for 5xx when `ERROR_BACKTRACES` is on. The type is boxed to one pointer, so the `Ok` path costs nothing, and `anyhow` is gone. Every request gets an `x-request-id`; failed requests are logged with method, URI, request id and origin (error for 5xx, warn for 501, debug for rejected requests) and sent to Sentry; and a database failure answers 500 instead of 400.
- The errors the server raised inline in more than one place became enums: `AuthError` for the authentication flows (one CSRF rejection, 403 everywhere), `TransactionError` for the shared-client case, and `ServerError`, which keeps serde and URL causes for the log instead of formatting them into the diagnostic.
- PRs: [#1422](https://github.com/HasteHealth/HasteHealth/pull/1422), [#1424](https://github.com/HasteHealth/HasteHealth/pull/1424).

### Request pipeline
- The server's FHIR client was rebuilt around one `Pipeline` of `Middleware` layers ending in a `Handler`, generic over a single `Backend` type that names the repository, search engine and terminology, with `Next` borrowing the rest of the chain so a hop costs no allocation. The old generic middleware chain in `fhir-client` was removed.
- A request is then dispatched to a typed lane (clinical, artifact, OperationDefinition, project auth, tenant auth, operation, capabilities), each a pipeline of its own. An interaction a lane does not serve answers not supported, and every variant is matched so a new one fails to compile unhandled.
- Writes refuse a body whose `resourceType` differs from the URL and an update whose body id differs from the URL id. The CapabilityStatement is cached per (tenant, project) rather than process-wide, since it lists a project's custom operations, and batch entries run with the audit repository attached.
- PRs: [#1078](https://github.com/HasteHealth/HasteHealth/pull/1078), [#1079](https://github.com/HasteHealth/HasteHealth/pull/1079), [#1109](https://github.com/HasteHealth/HasteHealth/pull/1109), [#1110](https://github.com/HasteHealth/HasteHealth/pull/1110), [#1089](https://github.com/HasteHealth/HasteHealth/pull/1089), [#1090](https://github.com/HasteHealth/HasteHealth/pull/1090).

### Sign-up, invitations and roles
- Self-service sign-up and login run through a verification-code flow with an optional Cloudflare Turnstile check and rate limiting. A `log` email backend writes the codes to the server log for local development, and `signup.enabled = false` turns self-service tenant creation off on a deployment that creates tenants with the CLI.
- A user a tenant creates for someone else is an invitation: the person proves they own the address and accepts or declines, and `emailVerified`, which clients cannot set, is required to log in.
- Writes to `User` enforce a role hierarchy: owners may modify any user, admins may modify admins and members, and a conditional update or delete needs an owner, so an admin cannot mint, demote or delete an owner. Tenant and project ids are lowercase letters and digits joined by single hyphens, at least three characters, so `{tenant}--{project}` is a valid subdomain label that splits back apart.

### Authentication hardening
- OIDC: only the `code` response type is advertised or accepted; a code issued to a PKCE request can only be redeemed with its verifier, and `S256` is computed as RFC 7636 writes it; a confidential grant is refused for a client with no stored secret; registered redirect URIs are regex-escaped before matching; an error raised before the redirect URI is validated is answered directly rather than redirected; the session id rotates on login, TOTP verification and the federated callback; a password change revokes the user's refresh tokens; and OAuth errors use the `error` and `error_description` names from RFC 6749.
- Federated login verifies that the provider's id token is signed with an asymmetric algorithm by a key in its JWKS and names the configured client id in `aud`. Haste Health's own id token took the same shape: `aud` is the client, `iss` is the project's issuer URL, and it carries `email`, `fhirUser`, tenant, project and role claims.
- Timing: auth string comparisons are constant time, and login and password reset take the same time whether or not the account exists. HTML pages are sent uncompressed so a CSRF token cannot be read off response sizes, the MFA create route checks CSRF, and the TOTP redirect stays local.
- The wrong-guess counter for one-time sign-up and login codes lived in the session, whose per-request copies lost increments under concurrent requests, so the five-attempt cap never tripped. Guesses are now counted in the database-backed rate limiter, keyed by the code's salted hash and serialized by a per-key advisory lock, before the code is compared.
- Smaller changes: Basic auth's cached tokens live five minutes; `$evaluate-policy` lets only owners and admins evaluate as another user; login, expired and security issue types map to 401 and 403 instead of 500; PostgreSQL error detail stays in the log rather than the OperationOutcome; scope approval reads the client application's stored id and scope; and tenant logo uploads have a size limit.

## Product and UX

## Platform and Runtime

### Indexing watermark and sequence index
- `max_safe_seq` makes one pass over `pg_locks` grouped by pid instead of a self-join that rescanned the lock table once per registrant: 20 to 170 ms per call became 0.8 ms under the same load. The registration marker lock now blocks instead of silently dropping a writer out of the watermark, and the indexing loop's idle sleep is configurable (`poll_interval_ms`).
- The resources sequence index leads with (tenant, project, sequence). A poll for a caught-up project whose sibling in the same tenant was a million rows ahead read about 805k buffers for zero rows; it now reads six.
- PRs: [#1018](https://github.com/HasteHealth/HasteHealth/pull/1018), [#1023](https://github.com/HasteHealth/HasteHealth/pull/1023).

### Search backend fixes
- `_count` and `_offset` are capped at what the backends accept, and wildcard characters in string searches are escaped on both Elasticsearch and PostgreSQL (the PostgreSQL fix came from an outside contributor, below), with a TestScript pinning the behaviour.
- A PostgreSQL B-tree entry must fit in a third of a page, and a long string such as a `ValueSet.description` does not: the CARIN Blue Button package has five, and inserting them stalled the project's indexing for good. The string prefix index is now over `LOWER(LEFT(value, 512))`, with the prefix and `:exact` clauses comparing that expression (a longer prefix compares the whole value, and `:contains` keeps the trigram index over the whole value). A batch insert that PostgreSQL rejects for its data (SQLSTATE classes 22, 23 and 54) is retried one resource per transaction and the rejected ones are parked where `$indexing-errors` lists them, rather than failing the batch on every pass.
- PRs: [#1025](https://github.com/HasteHealth/HasteHealth/pull/1025), [#1046](https://github.com/HasteHealth/HasteHealth/pull/1046), [#1264](https://github.com/HasteHealth/HasteHealth/pull/1264), [#1427](https://github.com/HasteHealth/HasteHealth/pull/1427).

### Validation performance
- Profile validation looks up each slice's discriminator definition once, on first use, and reuses it for the other values instead of walking the StructureDefinition per value. A benchmark and slicing tests came with it.
- PRs: [#1288](https://github.com/HasteHealth/HasteHealth/pull/1288).

### Custom operation runtime
- The Deno pool worker enters its tokio runtime for the whole loop, so warm isolates built between jobs no longer abort the process when V8 posts a delayed task.
- PRs: [#1092](https://github.com/HasteHealth/HasteHealth/pull/1092).

### Testing
- Property tests (`proptest`) cover the pure parsing and range code in six crates, with FHIR primitive generators behind a `testing` feature. They found and fixed four bugs: short years were not padded, impossible days such as `2023-02-30` now carry into the next month instead of failing, number range bounds lost their rounding tolerance above about seven significant digits, and a search number written with an exponent (`1e2`) got the implicit range of a plain integer.
- The TestScript runner gained HTTP-level assertions (`responseCode`, `headerField`, `contentType`), plain HTTP requests for URLs that are not FHIR interactions, and a poll-while extension that repeats a request while its status matches and honors `Retry-After`. An async-requests TestScript uses all three.
- `backend/testscripts/g10` holds 441 TestScripts for the checks of the ONC (g)(10) Standardized API test kit that a TestScript can express: SMART standalone, limited and EHR launch, the US Core 7 Single Patient API, Bulk Data, and v1 and fine-grained scopes. A `known-failures.txt` lists what does not pass yet, and a dedicated workflow runs the suite on the PostgreSQL backend.
- The e2e workflows share one build of the server across every suite, so no suite runs a binary built with different compiler settings.
- The US Core TestScripts moved under `backend/testscripts/us-core/<version>`, each naming the version it tests, and run in their own workflow on both search backends: 247 for 9.0.0 (218 examples, 29 profiles) and 241 for 7.0.0, whose package is installed exactly as HL7 publishes it. The (g)(10) suite runs against US Core 7.0.0, one of the versions the program certifies, waits for the CapabilityStatement to list the 46 US Core 7 profiles before the `supportedProfile` check, and asks for `_count=1000` on searches that can match more than one page, so a check no longer depends on which 50 results come first.
- `backend/testscripts/carin-bb/2.2.0` tests the CARIN Blue Button 2.2.0 package, added under `artifacts/r4` exactly as HL7 publishes it: every example it publishes (42) written with its profile claimed, and one conformance TestScript per profile the guide's server CapabilityStatement lists (11), each filling the profile's required and must-support elements and running every search parameter the guide adds. All 53 pass on PostgreSQL, in their own workflow.
- The runner's `--index-wait-ms` also waits before an operation, since `$everything`, `$expand` and `$viewdefinition-run` search for what they return, and tracks only the latest write per resource. An action that cannot run (a read of a fixture that a refused create never produced) fails its test in the TestReport instead of ending the run with no report, so `--allow-failure` covers it and the website shows what happened.
